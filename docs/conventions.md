# Conventions

## Code style

- **Kotlin:** ktlint with its defaults, applied to every Kotlin module by the
  [`kotlin-jvm` convention plugin](../buildSrc/src/main/kotlin/kotlin-jvm.gradle.kts).
  Run `./gradlew ktlintFormat` before pushing. CI runs `ktlintCheck` first and stops on failure.
  Don't add an `.editorconfig` override or another formatter. The project chose sane defaults over custom style.
- **Java (server):** no formatter is enforced. Follow the surrounding code: constructor
  injection with `final` fields, `record`s for DTOs, `var` for locals.
- **Comments explain *why*.** The codebase uses long KDoc/Javadoc that state the
  reasoning and the trap (see [`CatalogService`](../pixerion-server/src/main/java/io/modernia/pixerion/server/catalog/services/CatalogService.java)
  or [`MangaDexClient`](../pixerion-core/src/main/kotlin/io/modernia/pixerion/source/mangadex/MangaDexClient.kt)).
  Match that density when your code has a non-obvious reason behind it.

## Architecture rules

1. **Dependencies point inward to `core`.** `cli` and `server` never depend on each other.
2. **Front-ends are thin.** They parse input, call `core`, and render the result. Orchestration (such as `Downloader`) belongs in `core`.
3. **`domain` never imports an implementation.** Adapters live under `source.*`, and `CatalogRegistry` is the only composition point ([ADR-0014](adr/0014-single-catalog-registry-in-core.md)).
4. **Adapter = mapping, client = transport.** All OkHttp and serialization code lives in a sibling `*Client`.
5. **Java reaches `core` only through `interop`** (`BlockingCatalog`, `Refs`). Don't add a second `runBlocking` seam.
6. **No runtime reflection in CLI commands or the registry.** The GraalVM native image depends on metadata that is known at build time.
7. **No speculative abstractions.** Add an interface when a second implementation or a test seam needs one. An example of the second case is [`CatalogSources`](../pixerion-server/src/main/java/io/modernia/pixerion/server/catalog/components/CatalogSources.java).

## Error handling

The cross-cutting rule: **absence is a value; failure is an exception.**

| Situation | `core` | CLI | HTTP API |
|---|---|---|---|
| Book not found | `null` / empty list / empty flow | exit `1` | `200 []` |
| Unknown source name | `CatalogRegistry[x] == null` | exit `2` (usage error) | `400` (`UnknownSourceException`) |
| Source unreachable or malformed | `CatalogException` | exit `2` | `502` |
| Bad credentials | — | — | `401` (deliberately vague message) |

Adapters must translate transport errors into `CatalogException` and never leak
`IOException`, `SerializationException`, or HTTP status codes. The HTTP API returns
errors as RFC 7807 `ProblemDetail`.

## Testing

- **JUnit 5** everywhere. Kotlin tests use `kotlin.test` and `kotlinx-coroutines-test`.
- **No live network in tests.** Adapters run against an in-process OkHttp
  `MockWebServer` (see [`MangaDexCatalogTest`](../pixerion-core/src/test/kotlin/io/modernia/pixerion/source/mangadex/MangaDexCatalogTest.kt)).
  Front-ends substitute the source seam: `CatalogCommand`'s resolver in the CLI and the `CatalogSources` bean in the server.
- **Server tests run the real Flyway migrations on H2** (`MODE=PostgreSQL`) with
  `ddl-auto=validate`, so migrations are tested and drift between migrations and
  entities fails fast. Write migrations in SQL that runs on both Postgres and H2
  (for example `GENERATED BY DEFAULT AS IDENTITY`, not `BIGSERIAL`).
- `src/test/resources/application.properties` **replaces** the main one rather than
  merging with it. Any property the app needs has to be repeated there.
- Security behaviour that depends on the servlet container (the ERROR dispatch)
  needs a real-port test such as `ErrorDispatchTest`. MockMvc doesn't exercise it.
- Test method names are sentences: backticked in Kotlin
  (`` `find returns null for a 404` ``), snake_case in Java
  (`wrong_password_is_401`).
- Coverage: JaCoCo XML per module, uploaded to Qodana. Entry points (`MainKt`,
  `Application`) are excluded on purpose rather than covered by artificial tests.

## Dependencies

- Declare every dependency in [`gradle/libs.versions.toml`](../gradle/libs.versions.toml), never inline.
- Prefer mature JVM incumbents (OkHttp, kotlinx.serialization) over newer Kotlin-first libraries. **GraalVM native-image compatibility is a hard constraint** for anything `core` or `cli` uses.
- Qodana enforces licenses: the project is LGPL-3.0, and dependencies must be Apache-2.0 unless `qodana.yaml` is extended (see [ADR-0009](adr/0009-drop-sonarqube-cloud-static-analysis.md)).
- The JaCoCo version (`0.8.13`, required for JDK 25 bytecode) is pinned in three places: the convention plugin, `pixerion-cli/build.gradle.kts`, and `pixerion-server/build.gradle.kts`. Bump all three together.

## Commits and documentation

- **Conventional Commits** (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, …), with an optional module scope (`feat(core): …`).
- **Docs change with the code.** If a change touches a contract invariant, a module seam, the concurrency or rate-limit model, the on-disk layout, or build wiring, update [`ARCHITECTURE.md`](../ARCHITECTURE.md) (and the README if users see it) in the same PR. Update this site too if a page describes it.
- **ADRs** go in [`docs/adr/`](adr/README.md) when a real alternative was weighed. They are immutable once accepted: supersede them, don't edit them. Never reuse a retired number.
